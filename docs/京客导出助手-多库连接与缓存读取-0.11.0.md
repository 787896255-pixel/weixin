# 京客导出助手 0.11.0：多库连接与原程序缓存读取

日期：2026-10-24。延续“读取数据中”长时间不结束，以及复用原程序加载方式的任务。

## 本轮修复

### 1. 逐库收集访问材料

`windows_reader.acquire_keys` 旧实现对第一个通过校验的候选立即返回，因此可能只获得一部分库的材料。现在保留有效候选，继续检查未匹配的数据库首页，全部覆盖或达到时间、字节、取消边界后结束。诊断显示已匹配与目标首页数量，部分匹配与全部匹配分别说明。

同一访问材料可匹配多个库；不同材料也可逐个收集。没有输出或落盘材料值，没有移除 HMAC、页面、WAL 或副本完整性校验。此多库运行路径尚未在真实登录微信进程完成验收。

### 2. 先检查连接，再复制全文

识别到 Windows 微信目录布局后，先检查未完成的加密数据库首页。已经完成的文件、可复用的已解密副本仍能直接复用。新文件没有通过访问材料校验时，记录为未读并延后全文复制，直接报告连接状态；通过后才复制并做既有校验、解密和解析。该顺序避免先复制整个加密目录才发现当前进程不在运行。

### 3. 原导出器缓存适配继续补齐

- 在当前 Windows 用户的 LOCALAPPDATA、APPDATA 下，对 `wechat-exporter` / `wechatexport` 常见目录做有时间、数量、深度上限的 schema 探测；命中缓存后在账号选择中显示，可直接选择缓存数据库路径。
- `msg_rows.data` 仍按已观察到的 JSON 消息结构独立解析。
- `contact_overrides(username,nickname,...)` 中实际保存的名称用于对应会话或发送者；没有名称时保留 ID，不把群成员昵称作为群名。
- `msg_sync` 的会话同步标记、预期总数与实际行数用于说明缓存是否完整；部分缓存仍可查看。复用未变化文件时保留这份完整性说明。
- 多个无法确认账号的缓存文件分开标识账号，避免在同一目录下直接混合其聊天；用户显式填写账号范围时沿用该范围。
- 探测使用只读 immutable schema，忽略活动 WAL，所以没有命中不代表一定不存在缓存。正式读取仍复制并检查 DB 与 WAL。

这些格式依据上轮 REA 七函数分析，以及本轮从指定 EXE 读取的原始 SQL 字节。后者是字符串观察，不是新增原生函数分析。原程序完整 schema 的位置、长度、目标散列保存在开发机 `cache-schema-literals-20261024.json`。未加入原厂 EXE、DLL 或商业服务调用。
