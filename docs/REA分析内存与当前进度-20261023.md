# REA 分析内存与当前进度

日期：2026-10-23。目标为已安装的 QXExporter.exe 4.0.9；本文记录分析方法与实际证据，不表示京客导出助手已经完成复刻。

## 结论

当前不需要更换电脑。整包 JavaScript 的 REA 分析曾在 1024 MiB、4096 MiB 的独立工作堆设置下超限；现已改为从原脚本 AST 提取业务函数，分批、串行分析。65 个所选业务函数已完成解析，6 批均设置 `max_heap_mb: 1024`，没有解析失败或再次发生工作堆超限。

`max_heap_mb` 是 REA JavaScript 子进程的 V8 old-space 上限，不是本机总内存，也不控制 Hopper 的内存。1024 MiB 的设置不代表测得峰值恰好为 1 GiB。分批成功也不等于整份程序的跨函数语义已经完全恢复。

本机只读查询 `sysctl -n hw.memsize` 返回 25,769,803,776 字节，即 24 GiB。`memory_pressure` 的单次快照未显示交换入/出，报告 system-wide memory free percentage 42%；这只是当时的系统快照，不能代表所有分析时段的峰值。当前没有因该任务购买新硬件的依据。

## 为什么采用分批

普通 Babel 语法解析器可以解析原来的 390 KB 脚本；REA 在整包的静态分析阶段触发工作堆资源保护。结合分批结果，可以判断应先缩小分析作用域、减少一次保留的语义图，而不是按脚本体积推断硬件不足。尚未定位 REA 内部导致图增长的具体代码，不能声称已经修复其分析器。

后续沿用以下策略：

1. 保留原始文件、范围和散列，按功能切分。
2. 每次只分析一批，完成后导出 Evidence，再处理下一批。
3. 在函数和调用链之间逐步补充依赖，明确记录无法静态确定的动态调用。
4. 单个模块仍超限时，继续细分处理函数，再按实际需要提高该工作进程的上限。

## 已明确的两种登录

原前端存在两个不同的流程：

- **导出助手账号登录**：二维码登录、二维码刷新与轮询、手机号短信登录、用户与会员状态。桥接入口包括 `LoginQRCode`、`LoginCheckWechat`、`LoginSendSms`、`LoginSms`。它用于原软件的服务账号，不直接等于本地微信数据库已能读取。
- **电脑微信账号准备和读取**：已有缓存账号直接打开；新增账号检测当前微信登录状态、预备读取、必要时重启微信、等待登录、读取并显示账号确认页，然后进入聊天工作台。相关入口包括 `DetectNewAccountState`、`ArmPassiveCapture`、`RestartUserWeChatForKey`、`WaitForWeChatLogin`、`OpenAccountByCapture` 和 `OpenStoredAccount`。

Windows 首页“添加新的微信”在原脚本中进入上述检测/重新登录流程；已缓存账号可以进入详情并打开工作台。另有受控客户端准备流程，分为 trust、launch、login、scan、read、done。界面与桥接调用已能对应，原生函数内部行为仍需继续恢复。

## 原生 EXE 的独立阻塞

整份主程序的 Hopper 启动曾返回 `provider_timeout`：REA 当前启动等待上限为 120,000 ms。随后通过 Hopper 实际窗口的 Output log 读到：

> Background analysis ended in 2'09

窗口还显示 `Executing Python script "/tmp/rea-tqtJOL/bootstrap.py"`。这证明该次初始分析至少用了约 129 秒，超过 120 秒等待值；它不是 JavaScript 工作堆超限。

Evidence 导出后，`close_binary` 仍未获得桥接关闭确认。随后在 Hopper 尝试保存文档，官方 Demo 明确显示不允许保存，未生成或宣称保存原生快照。后续实际窗口已变为 `Untitled`、`0 labels`，原目标文档已不在该窗口中。保留 `/tmp/rea-tqtJOL`，未删除其内容；当前 MCP 连接的 cleanup 状态不能据此宣称已自动重置，下一次原生分析应使用新连接。

在用户先前授权的 REA 配置范围内，已将 `[mcp_servers.rea.env]` 的 `REA_HOPPER_STARTUP_TIMEOUT_MS` 设为字符串 `300000`，即原生启动等待从默认 120 秒增至 300 秒。配置文件修改前已备份到 `<本机 Codex 配置目录>/config.toml.rea-startup-timeout.backup.20261022T170403Z.4332199a27d5`；TOML 解析比较确认其他配置保持相同，客户端单次工具超时仍为 450 秒。新值由下一次新启动的 REA 进程读取，不会改变当前存活服务的环境。本轮尚未在新连接上重新运行主程序分析，不能宣称原生主程序已经反编译成功。
